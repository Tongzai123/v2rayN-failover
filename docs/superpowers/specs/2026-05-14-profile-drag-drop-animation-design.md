# 主列表拖拽排序动画初步设计

## 基本信息

- 日期：2026-05-14
- 目标项目：`v2rayN.Desktop`
- 设计范围：主界面配置列表的行拖拽排序动画
- 当前状态：初步设计，仅讨论，不实施
- 参考项目：`cc-switch-main`

## 背景

当前 `v2rayN.Desktop` 主界面服务器列表已经可以在启用“配置拖放排序”后通过拖拽调整行顺序。现有实现位于 `v2rayN/v2rayN.Desktop/Views/ProfilesView.axaml.cs`，核心流程是：

1. 鼠标按下时记录拖拽源行。
2. 鼠标移动超过阈值后调用 `DragDrop.DoDragDropAsync`。
3. Drop 到目标行时调用 ViewModel 移动节点顺序。

这个实现能完成排序，但视觉反馈较弱：用户看不到整行被抓起、跟随鼠标移动，也看不到其他行随着目标位置上下避让。

`cc-switch-main` 的拖拽排序体验更完整。它使用 React 的 `@dnd-kit`：

- `DndContext` 管理拖拽生命周期。
- `SortableContext` 和 `verticalListSortingStrategy` 管理纵向列表排序。
- `useSortable` 为每个卡片提供 `transform` 和 `transition`。
- 拖动项应用高亮、阴影和缩放，其他项通过位移产生避让动画。

Avalonia `DataGrid` 没有直接等价的 `dnd-kit` 机制，因此需要在现有 `DataGrid` 上自定义拖拽视觉层。

## 目标

实现接近 `cc-switch-main` 的拖拽体验：

- 鼠标按住一行后，用户能看到整行被抓起。
- 拖动过程中，被拖动行跟随鼠标上下移动。
- 源行和目标行之间的其他可见行平滑向上或向下避让。
- 松开鼠标后，列表按目标位置完成排序，并清理动画状态。
- 不改变现有排序持久化语义，不影响列宽、列顺序、筛选、统计列和当前节点标记。

## 非目标

- 不替换主列表控件为 `ListBox`、`ItemsControl` 或第三方列表控件。
- 不实现跨分组拖拽。
- 不改变代理链路、Tun、系统代理、路由规则、DNS、订阅或核心配置。
- 不改变数据库结构或节点数据格式。
- 初版不要求对不可见虚拟化行做动画。

## 推荐方案

推荐采用“自定义拖拽视觉层 + 可见行避让动画”的方案。

保留现有 `DataGrid` 和最终排序逻辑，但不再完全依赖系统拖放视觉。拖动开始后，视图层进入自定义拖拽状态：

1. 记录源行模型、源索引、源行高度、鼠标起点和源行屏幕位置。
2. 创建一个视觉上的“拖拽浮层”，显示被拖动行的整行快照或等效行内容。
3. 将真实源行设置为不可见占位状态，让原位置保留空行但不显示文字。
4. 鼠标移动时计算当前目标索引。
5. 对源行和目标行之间的可见 `DataGridRow` 设置 `RenderTransform`，让它们上下移动一个行高。
6. Drop 后调用现有移动逻辑，刷新列表并清理浮层、透明度和所有行位移。

这个方案可以在不替换 `DataGrid` 的前提下得到接近 `dnd-kit` 的体验。

## 备选方案

### 方案一：最小视觉增强

只在拖动时改变源行样式，例如半透明、边框高亮、鼠标光标变为抓取状态，并在目标行显示插入线。

优点：

- 改动小。
- 风险低。
- 不容易和 `DataGrid` 虚拟化冲突。

缺点：

- 没有“其他行避让”的动画。
- 与 `cc-switch-main` 的体验差距明显。

### 方案二：自定义拖拽视觉层

使用当前推荐方案，实现拖动浮层和可见行避让。

优点：

- 体验接近参考项目。
- 保留 `DataGrid` 的列、表头、横向滚动和现有绑定。
- 改动主要集中在 `ProfilesView.axaml.cs`。

缺点：

- 需要处理可见行测量、虚拟化、滚动和清理状态。
- 需要更细的手工验证。

### 方案三：替换列表控件

把主列表替换为更适合动画排序的 `ItemsControl` 或自定义列表。

优点：

- 动画控制最自由。
- 更容易实现完整的卡片式拖拽排序。

缺点：

- 会丢掉或重做 `DataGrid` 的列宽、列顺序、表头、横向滚动、排序、列显示隐藏等能力。
- 改动范围大，不适合当前本地改造目标。

## 交互设计

### 拖动启动

- 用户按住服务器列表某一行的数据单元格。
- 移动距离超过阈值后进入拖拽状态。
- 源行变为不可见占位，原位置看起来空出来。
- 浮层只显示被拖动行的文本内容，并跟随鼠标移动，不显示白色整条背景。

### 拖动过程

- 鼠标向上移动时，源行上方目标区间内的可见行向下避让。
- 鼠标向下移动时，源行下方目标区间内的可见行向上避让。
- 目标索引随鼠标所在行实时更新。
- 如果鼠标接近列表顶部或底部，可以在后续版本加入自动滚动。

### 拖动结束

- 松开鼠标后，如果目标索引有效且不同于源索引，则调用现有排序逻辑。
- 清理浮层、源行可见性、位移和拖拽状态。
- 如果取消拖拽或目标无效，则恢复原状，不提交排序。

## 技术设计

### 新增视图状态

建议在 `ProfilesView.axaml.cs` 中新增拖拽状态字段：

- `_isRowDragActive`
- `_dragSourceItem`
- `_dragSourceIndex`
- `_dragTargetIndex`
- `_dragStartPoint`
- `_dragCurrentPoint`
- `_dragRowHeight`
- `_dragOverlay`
- `_translatedRows`

这些状态只属于视图层，不进入 ViewModel。

### 拖拽浮层

浮层有两种实现方式：

1. 行内容快照：渲染一个与源行视觉接近的 `Border/Grid`，放在 `DataGrid` 上方。
2. 行控件复制样式：根据源行实际列宽构造一个临时行。

初版建议使用“行内容快照式浮层”：按列宽和列顺序显示文字，不显示整条白色背景、边框或阴影，让用户感知为拖着这一行字上下移动。这样实现更稳。

初版浮层按当前可见列和当前列显示顺序生成近似行内容，不尝试复制 `DataGridTemplateColumn` 内的所有标签、图标和交互状态。横向滚动状态下，浮层应至少保持宽度、列顺序和文本不遮挡主列表；如果实现阶段无法可靠取得内部水平滚动偏移，则把“完全列像素对齐”明确记录为后续增强，不作为第一阶段阻断项。

### 行避让动画

对当前可见的 `DataGridRow` 应用 `TranslateTransform`：

- 源索引小于目标索引：区间 `(sourceIndex, targetIndex]` 的行上移一个行高。
- 源索引大于目标索引：区间 `[targetIndex, sourceIndex)` 的行下移一个行高。
- 其他行位移归零。

动画可以使用 Avalonia `Transitions` 或短时 `RenderTransform` 动画。初版建议使用 120ms 到 180ms 的位移动画，避免拖动过程中产生拖泥带水的延迟。

拖拽过程中不要因为某一行当前偏移回到 0 就立即移除该行的 `RenderTransform`，否则容易出现瞬移。更稳的策略是拖拽期间保留已接管的 `TranslateTransform`，把 `Y` 动画回 0；拖拽结束、取消或捕获丢失后，再统一恢复原始 `RenderTransform`。

### 目标索引计算

优先使用鼠标位置命中的 `DataGridRow`：

- 用 `PointerEventArgs.GetPosition(lstProfiles)` 得到鼠标在 `DataGrid` 内的位置。
- 通过 `InputHitTest(position)` 或 `GetVisualAt(position)` 命中当前位置下方的视觉元素，再向上查找当前鼠标所在 `DataGridRow`。
- 从 `DataContext` 得到 `ProfileItemModel`。
- 使用 `ViewModel.ProfileItems.IndexOf(targetItem)` 得到目标索引。

如果命中空白区域，保持上一次有效目标索引。

不要在拖拽激活后依赖 `PointerEventArgs.Source` 计算目标行。指针捕获到 `lstProfiles` 后，事件源可能不再是鼠标下方的 `DataGridRow`，继续使用事件源会导致目标索引停留在源行或失效。

### 提交排序

Drop 时继续复用现有 ViewModel 移动逻辑：

- 普通分组：调用现有 `MoveServerTo` / `ConfigHandler.MoveServer` 路径。
- 故障转移分组：保留现有 `FailoverGroupManager.MoveQueueItem` 路径。

动画层只负责视觉，不直接修改排序数据。

提交排序时优先调用 `MoveServerTo(string? sourceIndexId, ProfileItemModel targetItem)` 重载。相比传入拖拽开始时的列表索引，`IndexId` 在刷新、筛选、故障转移分组和显示排序状态下更稳定，也与现有 ViewModel 内部按 `IndexId` 查找源节点的实现一致。

## 风险与边界

### DataGrid 虚拟化

`DataGrid` 只生成可见行。初版只对可见行做避让动画。拖到不可见区域时，必须通过自动滚动或保持目标索引不变来处理，不能假设所有行都在视觉树中。

### 横向滚动

理想状态下，浮层需要与当前横向滚动位置保持一致，否则用户可能看到浮层内容和列错位。第一阶段可以接受“近似整行浮层”：浮层按当前可见列顺序和列宽展示文本，但不承诺和横向滚动后的真实单元格逐像素对齐。手工验证必须覆盖横向滚动场景，确认浮层不会遮挡操作、不会残留，也不会影响排序提交；完全对齐可作为后续增强。

### 筛选与表头排序

如果列表处于筛选状态，拖拽排序只影响当前可见列表对应的持久排序值。表头排序状态下进行拖拽可能让用户困惑，后续可考虑：

- 表头排序后禁用手动拖拽。
- 或拖拽时清除表头排序状态。

初版建议保持现有行为，只在文档和测试中记录风险。

### 多选

初版只移动鼠标按住的单行，不做多选批量拖拽。

### 代理安全

该功能只影响 UI 排序体验和排序持久化，不进入代理链路。不会改变节点协议、路由、DNS、Tun、系统代理、订阅、证书或核心更新逻辑。

## 验证计划

### 自动化验证

- 保留现有 `ProfileDragDropSortTests`，覆盖源行定位。
- 可新增纯函数测试，用于验证源索引、目标索引到避让区间的计算：
  - 源在上，目标在下。
  - 源在下，目标在上。
  - 源等于目标。
  - 目标无效。

### 编译验证

- `dotnet build v2rayN\v2rayN.Desktop\v2rayN.Desktop.csproj --no-restore`
- `dotnet test v2rayN\ServiceLib.Tests\ServiceLib.Tests.csproj --no-restore`

### 手工验证

- 启用拖放排序并重启。
- 从上往下拖动一行，观察中间行是否上移避让。
- 从下往上拖动一行，观察中间行是否下移避让。
- 拖动后松开，验证顺序持久化。
- 横向滚动后拖动，验证浮层不遮挡操作、不残留，并记录是否和当前列位置完全对齐。
- 列顺序调整后拖动，验证浮层仍能正确显示。
- 在故障转移分组中拖动队列项，验证不破坏优先级。

1. 设计拖拽状态机和行位移计算纯函数。
2. 添加可测试的避让区间计算。
3. 在 `ProfilesView` 中接管拖拽过程，先实现源行高亮和插入位置反馈。
4. 增加拖拽浮层，并明确横向滚动下的第一阶段对齐边界。
5. 增加可见行避让动画。
6. 处理取消拖拽、Drop 后清理和异常清理。
7. 执行编译、单元测试和手工拖拽验证。

## 开放问题

- 浮层是否需要完全复制真实行所有列模板，还是只需要近似整行视觉。
- 表头排序状态下是否允许拖拽排序。
- 是否需要只允许从一个拖拽手柄开始拖动，避免和双击激活、选择、右键菜单冲突。
- 是否需要拖动到列表边缘时自动滚动。

## 推荐结论

建议先实现“方案二：自定义拖拽视觉层”的第一阶段：源行高亮、拖拽浮层、可见行避让动画。不要替换 `DataGrid`，也不要先做多选拖拽或复杂自动滚动。这样能明显提升用户感知，同时把风险控制在主界面视图层。
