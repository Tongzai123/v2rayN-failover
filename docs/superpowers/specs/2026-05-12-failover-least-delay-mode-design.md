# 故障分组延迟转移模式设计

## 背景

当前故障分组已经具备故障队列、活动故障组、主界面故障转移开关，以及后台真实延迟健康探测能力。现有主界面开关只有开启/关闭两态，开启后使用故障队列顺序生成虚拟 fallback `PolicyGroup`，并由健康探测维护节点状态和延迟。

本次设计新增第三种模式：延迟转移。延迟转移会复用现有探测链路，在每轮探测完成后从故障队列已启用节点中选择延迟最低的节点，并让该节点在运行态列表和核心生成顺序中处于第一位。

## 目标

- 主界面把原“故障转移”开关升级为三段模式按钮：`故障转移 | 关闭 | 延迟转移`。
- `关闭` 被选中时按钮背景为蓝色。
- `故障转移` 和 `延迟转移` 被选中时按钮背景为绿色。
- 三段按钮右侧显示当前活动故障分组名称；没有活动故障组时显示现有“请先设置活动故障组”文案。
- 延迟转移只处理故障队列中已启用的节点，不处理故障分组里的未启用候选节点。
- 延迟转移模式下不显示 `P*` 优先级标签；健康状态标签继续显示。
- 关闭或切回故障转移后，列表顺序恢复用户原本维护的故障队列顺序。

## 非目标

- 不修改 Tun、系统代理、路由规则、DNS、TLS、订阅下载、证书或核心更新逻辑。
- 不把未加入故障队列的候选节点纳入延迟转移排序。
- 不依赖核心内置 `LeastPing` 替代 UI 列表排序，因为用户需要看到选中节点处于列表第一位。
- 不在延迟转移模式下显示 `P*`，避免把运行态延迟选择误读为用户手动优先级。

## 状态模型

现有配置使用 `FailoverEnabled: bool` 表达是否启用故障转移。新增三态后，不建议继续用布尔值承载模式，应新增明确模式字段，例如：

```csharp
public enum EFailoverMode
{
    Off = 0,
    Failover = 1,
    LeastDelay = 2,
}
```

推荐在 `Config` 中新增 `FailoverMode` 字段。旧配置兼容规则：

- 旧配置 `FailoverEnabled == false` 时迁移为 `Off`。
- 旧配置 `FailoverEnabled == true` 时迁移为 `Failover`。
- 旧字段可在兼容期保留读写桥接，后续再考虑移除。

这样可以避免 `FailoverEnabled=true` 时无法区分“故障转移”和“延迟转移”的问题。

## UI 设计

主界面消息区现有的“故障转移”文字和二态开关改为三段模式按钮：

```text
[ 故障转移 | 关闭 | 延迟转移 ]  活动故障组名称
```

选中态规则：

- `关闭`：选中段为蓝色背景。
- `故障转移`：选中段为绿色背景。
- `延迟转移`：选中段为绿色背景。
- 三段按钮始终有且只有一个当前模式；当前模式段按上述规则上色，另外两个非当前模式段使用默认按钮背景。

三段按钮本身已经表达当前模式，所以左侧不再显示“当前为...”文字。

故障分组列表标签规则：

- `故障转移` 模式：已启用队列节点继续显示 `P1`、`P2` 等优先级标签。
- `延迟转移` 模式：已启用队列节点不显示 `P*` 标签。
- `关闭` 模式：沿用现有列表显示方式，建议仍显示 `P*`，表示用户维护的静态队列顺序。
- 健康状态标签不受影响，继续显示“正常 / 故障 / 探测中 / 未知”。

## 排序设计

推荐使用“运行态重排”，不直接改写 `FailoverGroupItem.Sort`。

故障队列原始顺序仍由 `Sort` 保存，用于表示用户手动维护的优先级。延迟转移模式下，系统在读取队列后基于探测结果计算一个运行态顺序：

1. 获取活动故障组已启用队列节点，按原始 `Sort` 得到基础顺序。
2. 每轮健康探测完成后，使用成功节点中的 `LastDelay` 选出最低延迟节点。
3. 如果最低延迟节点不是基础顺序第一位，则仅在运行态顺序中把最低延迟节点与第一位节点互换。
4. UI 列表和核心虚拟组生成都使用该运行态顺序。
5. 关闭或切回故障转移后，重新使用原始 `Sort` 顺序，列表自然恢复。

失败、未知、探测中或延迟值无效的节点不参与“最低延迟”候选。若没有任何成功延迟结果，则保持原始队列顺序。

该方案不需要保存恢复快照，也不会因为应用异常退出导致用户维护的队列顺序损坏。

## 数据流

模式切换：

1. 用户点击三段按钮。
2. `MsgViewModel` 接收目标模式。
3. 切到 `Off` 时停止健康探测、保存配置、发布重载和故障状态刷新事件。
4. 切到 `Failover` 或 `LeastDelay` 时先校验当前节点、活动故障组、队列有效性和核心类型一致性。
5. 校验成功后保存模式、启动健康探测、发布重载和故障状态刷新事件。

延迟转移探测：

1. `FailoverHealthService` 继续复用现有批量真实延迟探测。
2. 探测完成后写回 `LastStatus` 和 `LastDelay`。
3. 若当前模式为 `LeastDelay`，发布健康变更事件后列表刷新时使用运行态顺序。
4. 核心配置生成时同样按运行态顺序生成虚拟 fallback `PolicyGroup`。

## 组件影响

- `Config`：新增三态模式字段，保留旧布尔兼容。
- `MsgViewModel`：从布尔开关绑定改为三态模式绑定；保留现有校验与启动/停止探测流程。
- `MsgView.axaml` / `.cs`：替换 `ToggleSwitch` 为三段模式按钮或等价控件。
- `FailoverGroupManager`：新增根据当前模式返回运行态队列顺序的方法；原始 `Sort` 不变。
- `ProfilesViewModel`：延迟转移模式下隐藏 `P*` 标签，并使用运行态顺序展示活动故障组。
- `FailoverHealthService`：探测逻辑继续复用，必要时在探测完成后触发状态刷新。
- 资源文件：新增三段按钮相关文案，例如“延迟转移”。

## 错误处理

- 没有活动故障组时，切到 `Failover` 或 `LeastDelay` 应回退到 `Off` 并提示用户先设置活动故障组。
- 队列为空、当前核心不支持或队列节点核心类型混用时，沿用现有校验提示并回退到 `Off`。
- 延迟探测没有成功结果时，不改变运行态第一节点，保持原始队列顺序。
- 探测取消时不写失败状态，不触发最低延迟切换。
- 若活动故障组失效，自动回退 `Off`，停止健康探测。

## 测试计划

服务层测试：

- 旧 `FailoverEnabled` 到新三态模式的兼容迁移。
- `Off / Failover / LeastDelay` 三种模式下虚拟组构建入口行为。
- 延迟转移只从已启用队列节点选择最低延迟。
- 最低延迟节点与第一节点互换运行态顺序，不修改数据库 `Sort`。
- 无成功延迟结果时保持原始顺序。
- 切回 `Failover` 或 `Off` 后恢复原始顺序。
- 延迟转移模式下 `P*` 标签隐藏，故障转移模式下 `P*` 标签显示。

## 代理安全影响评估

本设计会影响活动故障组虚拟 `PolicyGroup` 的子节点顺序，从而改变当前代理入口的优先选择。但它不修改 Tun、系统代理、路由规则、DNS、TLS、订阅下载、证书信任或核心更新策略。

延迟探测继续复用已有批量真实延迟健康探测，并保持 `suppressFailover: true`，避免被活动 fallback 组兜底后误判真实节点状态。无有效队列或核心类型不一致时必须阻止启用，避免静默直连或生成不可用配置。
