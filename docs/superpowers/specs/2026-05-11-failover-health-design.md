# 故障队列健康状态二阶段设计

## 目标

第二阶段在第一阶段“核心 fallback 可用闭环”的基础上，补充 v2rayN 外层健康状态与主动检测能力。用户在故障分组中应能看到每个队列节点的状态：`正常`、`故障`、`探测中`、`未知`，并继续看到 `P1/P2/P3` 优先级。

本阶段只解决“状态可见”和“恢复可确认”。不在本阶段动态改写 fallback 队列、不强行触发核心回切、不承诺中断或迁移已有连接。这些控制类能力放到第三阶段。

## 当前依据

第一阶段已通过手工验证：

- 可以创建故障分组。
- 普通节点可以复制到故障分组。
- 故障组节点可以加入故障队列。
- 右键菜单“移至 -> 上移/下移/置顶/置底”可以改变 `P1/P2`。
- 可以设置活动故障组并开启故障转移。
- `P1` 故障后，请求可以落到 `P2`。

当前缺口：

- UI 不能确认当前真实工作节点。
- UI 不能确认 `P1` 恢复后是否已恢复正常。
- Desktop 拖拽排序开关未暴露，但菜单排序路径已可用，不阻塞二阶段。

## 方案选择

### 推荐方案：外层轻量健康探测

新增 `FailoverHealthManager` 或等价服务，只在 `Config.FailoverEnabled = true` 且存在有效活动故障组时运行。它按活动故障队列读取真实节点，使用现有测速链路的“真实延迟测试”思路，为每个节点启动临时测速核心并访问 `SpeedTestItem.SpeedPingTestUrl`。

优点：

- 不依赖 Xray 或 sing-box 是否暴露 fallback 内部状态。
- 与现有 `SpeedtestService` 使用同类测试 URL 和临时核心机制，安全边界清楚。
- 能确认节点是否可用，足够支撑 `正常/故障/探测中/未知` UI。

代价：

- 周期探测会额外启动临时核心进程，必须控制频率和并发。
- 它只能说明“外层探测可用”，不能百分百证明主运行核心当前正在使用哪个子节点。

### 不采用方案：解析核心内部状态

不尝试从 Xray 或 sing-box 内部 API 读取 fallback 当前子节点。原因是两类核心的状态暴露能力和语义不同，且第一阶段当前实现没有统一状态接口。强行解析会增加不稳定依赖。

### 不采用方案：二阶段直接重排核心队列

不在二阶段根据健康状态动态剔除或重排 fallback 子节点。原因是这会进入“外层熔断控制”范畴，需要更完整的连接不中断策略、重载策略和恢复策略，放到第三阶段更稳。

## 状态机

节点状态使用字符串字段保存，取值：

- `Unknown`：尚未检测或状态不可判断。
- `Normal`：最近一次探测成功。
- `Failed`：连续失败达到阈值，处于故障状态。
- `Probing`：冷却期结束后正在做半开探测。

状态转移规则：

- 初始状态为 `Unknown`。
- 探测成功：状态改为 `Normal`，失败次数清零，清空冷却截止时间，记录 `LastSuccessTime`。
- 探测失败：失败次数加一，记录 `LastFailureTime` 和 `LastFailureReason`。
- 连续失败次数达到 `2`：状态改为 `Failed`，写入冷却截止时间。
- 冷却结束：状态改为 `Probing`，允许一次探测。
- `Probing` 成功：状态改为 `Normal`。
- `Probing` 失败：状态改回 `Failed`，冷却时间进入下一档。

冷却策略：

- 首次故障冷却 `60` 秒。
- 连续故障后退避为 `120` 秒。
- 再失败后退避为 `300` 秒。
- 最大冷却 `300` 秒。

## 数据设计

在现有 `FailoverGroupItem` 基础上补充字段：

- `FailureCount`: `int`，连续失败次数。
- `CooldownUntilTime`: `long?`，冷却截止时间，使用 Unix 毫秒或 ticks，具体格式在实施计划中与项目现有时间字段保持一致。
- `LastSuccessTime`: `long?`，最近一次探测成功时间。
- `LastProbeTime`: `long?`，最近一次探测开始或完成时间。
- `LastDelay`: `int`，最近一次成功探测延迟，单位毫秒；失败时可保持上次成功值或置为 `0`，实施时需固定一种语义。

保留现有字段：

- `LastStatus`
- `LastFailureTime`
- `LastFailureReason`
- `Memo`

## 探测服务设计

新增后台服务职责：

- 监听故障转移开关和活动故障组变化。
- 开启故障转移时启动周期探测。
- 关闭故障转移、活动故障组失效或应用退出时停止探测。
- 每轮只检测活动故障组中 `Enabled = true` 且真实节点仍存在的队列项。
- 默认每 `30` 秒扫描一次队列，但对 `Failed` 节点遵守冷却时间，冷却未结束不探测。
- 并发默认 `1`，避免频繁启动多个临时核心进程。

探测方式：

- 优先复用 `SpeedtestService` 中的真实延迟测试链路。
- 如需重构，提取一个可被 `SpeedtestService` 和 `FailoverHealthManager` 共同调用的节点探测方法，避免复制大量测速代码。
- 探测 URL 使用现有 `Config.SpeedTestItem.SpeedPingTestUrl`。
- 探测失败原因应记录为简短文本，例如 `timeout`、`core-start-failed`、`request-failed`，避免写入敏感 URL、订阅内容或节点密钥。

## UI 设计

故障分组节点列表中，在别名前显示状态标签：

- `正常`：绿色背景。
- `故障`：红色背景，样式参考普通分组的“活动”标签。
- `探测中`：黄色或中性色背景。
- `未知`：灰色或中性色背景。
- `P*`：保持绿色背景，继续表示队列优先级。

标签规则：

- 只有故障分组里的队列节点显示健康状态标签。
- 未加入故障队列的候选节点不显示健康状态标签。
- 未开启故障转移时，可显示历史状态，但不把任何节点标记为“当前工作节点”。
- 本阶段不新增“当前实际工作节点”强标签；如果需要提示，可使用“当前优先入口”一类谨慎文案，仅对 `P1` 表示配置优先级，不声称核心当前一定使用它。

## 与核心 fallback 的关系

第二阶段不改变第一阶段的核心配置构建策略：

- `Config.FailoverEnabled = true` 时仍由虚拟 `PolicyGroup` 作为入口。
- 子节点顺序仍按 `FailoverGroupItem.Sort` 生成。
- 健康探测只更新状态字段和 UI，不修改 `ChildItems`。
- 无有效队列时仍阻止开启故障转移，避免静默直连。

## 代理安全影响评估

本阶段会额外发起健康探测请求，但不改变 Tun、系统代理、路由规则、DNS、TLS、证书、订阅下载或核心更新策略。

安全边界：

- 探测必须通过节点对应的临时核心链路发出，不能为了省事改成直连目标 URL。
- 探测失败不得导致主代理入口静默切到直连。
- 日志和状态字段不得写入订阅链接、节点密钥、完整分享链接或 Token。
- 活动故障组为空、有效队列为空或核心类型不支持时，探测服务必须停止或跳过。

## 测试策略

自动化测试：

- 测试状态机：连续失败两次进入 `Failed`。
- 测试成功恢复：`Probing` 成功后进入 `Normal`。
- 测试冷却退避：`60s -> 120s -> 300s`。
- 测试读取队列：失效 `SourceProfileId` 不参与探测。
- 测试 UI 模型映射：`LastStatus` 正确转换为状态标签字段。

手工验证：

- 开启故障转移后，活动故障组节点状态能从 `未知` 更新为 `正常` 或 `故障`。
- `P1` 故障后，UI 显示 `故障 P1`，请求仍可落到 `P2`。
- 恢复 `P1` 后，冷却结束并探测成功，UI 显示 `正常 P1`。
- 关闭故障转移后，健康探测停止，不再持续启动临时核心。

## 二阶段验收标准

- 用户能在故障分组中看到队列节点的健康状态标签。
- `P1` 故障后，外层状态能显示为 `故障`。
- `P1` 恢复后，冷却结束并探测成功，外层状态能恢复为 `正常`。
- 健康状态更新不会破坏第一阶段 fallback 代理链路。
- 验证记录和代理安全影响评估写入 `_local_changes/007-failover-health/`。
